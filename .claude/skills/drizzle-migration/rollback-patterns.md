# Rollback Patterns

How to reverse each type of migration operation.

## Auto-Reversible Operations

These can be mechanically reversed:

| UP Statement | DOWN (Rollback) Statement |
|---|---|
| `CREATE TABLE IF NOT EXISTS x (...)` | `DROP TABLE IF EXISTS x CASCADE` |
| `ALTER TABLE x ADD COLUMN y type` | `ALTER TABLE x DROP COLUMN IF EXISTS y` |
| `ALTER TABLE x ADD COLUMN y type NOT NULL DEFAULT val` | `ALTER TABLE x DROP COLUMN IF EXISTS y` |
| `CREATE INDEX IF NOT EXISTS idx ON x (...)` | `DROP INDEX IF EXISTS idx` |
| `CREATE UNIQUE INDEX IF NOT EXISTS idx ON x (...)` | `DROP INDEX IF EXISTS idx` |
| `ALTER TABLE x ADD CONSTRAINT c ...` | `ALTER TABLE x DROP CONSTRAINT IF EXISTS c` |
| `CREATE EXTENSION IF NOT EXISTS ext` | `DROP EXTENSION IF EXISTS ext` |
| `COMMENT ON TABLE x IS 'text'` | *(no-op — skip)* |
| `ALTER TABLE x ALTER COLUMN y SET DEFAULT val` | `ALTER TABLE x ALTER COLUMN y DROP DEFAULT` |
| `ALTER TABLE x ALTER COLUMN y SET NOT NULL` | `ALTER TABLE x ALTER COLUMN y DROP NOT NULL` |

## Non-Reversible Operations (require manual intervention)

| Operation | Why Not Reversible | What To Do |
|---|---|---|
| `DROP TABLE x` | Data is gone | Restore from backup, or accept data loss |
| `DROP COLUMN y` | Data is gone | Restore from backup, or accept data loss |
| `ALTER COLUMN y TYPE newtype` | Old data may be truncated/converted | Add column with old type, backfill from new, drop new, rename old |
| `INSERT INTO ...` / `UPDATE ...` | Data changes can't be auto-reversed | Write inverse DML manually (DELETE/UPDATE with WHERE) |
| `CREATE INDEX CONCURRENTLY` | Can't be in transaction, so can't be part of rollback transaction | `DROP INDEX IF EXISTS idx` separately |
| `ALTER TYPE ... ADD VALUE` | PG doesn't support removing enum values | Recreate the type (requires column migration) |

## Rollback SQL Template

When generating rollback SQL for a migration:

```sql
-- Rollback for NNNN_<tag>.sql
-- Generated by /drizzle-migration skill
-- WARNING: Review carefully before executing!

BEGIN;

-- Reverse statements in REVERSE order (last applied = first rolled back)
-- Statement 3 (was: CREATE INDEX)
DROP INDEX IF EXISTS idx_my_table_column;

-- Statement 2 (was: ALTER TABLE ADD COLUMN)
ALTER TABLE my_table DROP COLUMN IF EXISTS new_column;

-- Statement 1 (was: CREATE TABLE)
DROP TABLE IF EXISTS my_table CASCADE;

COMMIT;
```

**Key rules**:
1. Reverse in opposite order (last change first)
2. Use `IF EXISTS` on every statement
3. Wrap in a transaction
4. Use `CASCADE` on `DROP TABLE` to handle dependent FKs
5. For non-reversible operations, add a comment:

```sql
-- MANUAL ROLLBACK REQUIRED: Cannot auto-reverse ALTER COLUMN y TYPE
-- Original: ALTER COLUMN y TYPE varchar(50) USING y::varchar(50)
-- To reverse: Add column y_old, backfill from y, drop y, rename y_old to y
```

## Safe Column Removal Pattern (multi-step)

Never drop a column in a single migration. Use this 3-step pattern:

**Step 1: Stop Writing** (deploy code change, no migration)
- Remove all writes to the column in application code
- Column still exists, reads still work

**Step 2: Stop Reading** (deploy code change, no migration)
- Remove all reads from the column
- Verify via OTel traces that no queries reference it

**Step 3: Drop Column** (migration)
- Now safe to `ALTER TABLE ... DROP COLUMN`
- Column has no code dependencies

This pattern prevents production errors from column removal.

## Safe Type Change Pattern (multi-step)

For changing a column's data type on a populated table:

**Step 1**: Add new column with target type
```sql
ALTER TABLE x ADD COLUMN y_new target_type;
```

**Step 2**: Backfill in batches (separate script, not migration)
```sql
UPDATE x SET y_new = y::target_type WHERE y_new IS NULL LIMIT 1000;
```

**Step 3**: Swap columns
```sql
ALTER TABLE x RENAME COLUMN y TO y_old;
ALTER TABLE x RENAME COLUMN y_new TO y;
```

**Step 4**: Drop old column (after verification period)
```sql
ALTER TABLE x DROP COLUMN y_old;
```

## Project-Specific Notes

### Drizzle Kit Journal Hash
Drizzle Kit tracks migrations by SHA-256 hash. If you need to manually write a rollback and run it:
- Do NOT modify the original UP migration file
- Run rollback SQL via `psql` or a one-time script in `backend/scripts/`
- The journal (`_journal.json`) does NOT track rollbacks — it only records forward migrations

### Reconciliation History
The project has a reconciliation pattern (`0007_reconcile_manual_tables.sql`). If a rollback puts the DB in a state that diverges from the journal, you may need a new reconciliation migration. See journal-troubleshooting.md.

### Where to Store Rollback Files
Rollback SQL should be presented to the user inline (not saved to a file) unless they request persistent storage. If they do, suggest:
- `backend/drizzle/rollbacks/NNNN_rollback.sql`
- This directory is not currently gitignored, so files will be committed
